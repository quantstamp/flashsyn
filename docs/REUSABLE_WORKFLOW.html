FlashSyn

Reusable Workflow

How to point FlashSyn at a new protocol. This captures the current (pre-modernization) procedure so the AI-augmented tooling in PROPOSAL.md has a concrete baseline to automate.

Source of truth: the flashsyn-euler repo (the proceduralized "Pro" line), read alongside the older research-flashsyn engine. Nothing here has been executed yet — see Environment & reproducibility for the setup gaps found.

1. Which codebase is the reusable one

Two prior repos sit in this directory:

RepoRole
research-flashsyn (2023)Original paper artifact. Full engine + ~17 hand-written benchmarks. Research-grade.
flashsyn-euler (2024)Reusable line. Same engine, wrapped in a template.py fill-in-the-blanks form. Its README calls it "a boilerplate and a stable version."

Use flashsyn-euler as the base. Treat research-flashsyn's 17 benchmarks as a regression suite / reference examples, not as the starting skeleton. (The two use contradicting action styles; do not blend them.)

2. The core idea

FlashSyn splits cleanly into two halves joined by one convention:

  • Fixed engine (protocol-agnostic, never edited): the synthesizer, the polynomial approximators, the dependency checker, and the Foundry harness.
  • Authored per protocol (the expert work): a Foundry test that forks the chain, plus a Python "action model" describing each protocol action.

The seam between them is a two-part contract:

  1. $$ placeholders in Solidity snippets mark the numeric parameters FlashSyn will search over.
  2. revert("FlashSyn: <numbers>") is the data channel. Actions deliberately revert with a string starting FlashSyn; the Python side regex-scrapes forge's FAIL. Reason: line, extracts the numbers, and uses them as measured state changes. A revert reason without FlashSyn means the action reverted for real → that sample is infeasible.

Because of this contract, adapting to a new protocol requires no engine changes — only the two authored files below.

3. What you author (two files)

3a. Foundry test — src/foundryModule/src/test/attack.t.sol

Forks the target chain at the exploit block and sets up the attacker (starting balances, any prank / minter setup). The runner is src/foundryModule/run.sh <name>, which wraps:

forge test --match-contract <name> --fork-url <RPC> --fork-block-number <N>

RPC endpoints and the fork block are the only chain configuration. For Euler: contract euler, mainnet, block 16818064.

3b. Action model — a copy of src/FlashSynProActions/template.py

template.py is a numbered-TODO form; EulerActions.py is the same form filled in for Euler and serves as the worked reference. You write one base class plus one subclass per protocol action.

Base class (top of the file):

FieldMeaning
initialBalancesAttacker's starting balances, e.g. {"USDC": 400000000} (decimals ignored).
TokenPricesPrice of each token of interest for profit weighting; stablecoins = 1.0.
start_strThe Solidity header — imports, interfaces, contract decl, setUp() — up to the first action.
calcProfit(stats)Objective function: how measured end-state → profit number.

One subclass per action (deposit, borrow, donate, liquidate, …):

Field / methodMeaning
numInputs, rangeHow many parameters this action exposes, and the search bounds for them.
tokensIn / tokensOutWhich attacker tokens the action consumes / produces.
actionStr()Solidity to execute the action, with $$ where a searched parameter goes.
collectorStr()Solidity that runs the action and reverts with a "FlashSyn: …" string carrying the measured state delta. This is how the engine learns the action's input→output behavior.
transit(inputs, actionList)How the action updates the abstract balance vector, using the approximator's predicted output.

main() wires it up: lists the actions, declares each action's prestate dependencies (which other actions change its inputs — from step 2 below), then calls initialPass() and later the synthesizer.

4. Run procedure (five steps)

From the flashsyn-euler root, matching its README:

  1. Compile the Foundry script. 
    cd src/foundryModule && ./run.sh <contract> <ETH|BSC|Fantom|Polygon> <fork-block>
# Euler: ./run.sh euler ETH 16818064
  2. Compute action dependencies. 
    python3 src/dependencyCheck.py "./run.sh <contract> <chain> <fork-block> -vvv"
    Runs the actions twice under vm.record() / vm.accesses(), diffs the storage read/write sets, and reports which actions actually influence which others. Paste that graph into the actionN_prestate_dependency lists in main(). (Unsure? Conservatively mark every action as dependent on every other — correct, just slower.)
  3. Collect initial data points. 
    python3 src/FlashSynProActions/EulerActions.py
    initialPass() samples each action (and its dependency sequences) on the fork, gathering ~500–2000 input→output points via the collector reverts. Cached under initialDataPoints/<name>/. Ensure that folder exists first.
  4. Run the synthesis. In the actions file, comment out the initialPass() call and uncomment the Synthesizer.synthesis(maxSynthesisLen, Pruning, CounterExampleLoop, …) block, then: 
    python3 src/FlashSynProActions/EulerActions.py > EulerLog.txt
  5. Read the result. The tail of EulerLog.txt prints the best profit and the winning action sequence + parameters.

5. What the engine does (under the hood)

Useful for debugging, not something you edit:

  • Action → Solidity → fork. buildDVDattackContract stitches actions' actionStr() into a full attack; the collector variant runs the prefix as real calls and the last action instrumented. Each sampled parameter tuple becomes its own testExampleN_(), so one forge test measures many samples at once.
  • Data points → polynomial surrogate. Sampled input→output points (keyed by a canonicalized AttackDAG so equivalent sequences share data) are fit per-action into a polynomial approximation of profit over the parameters.
  • Search. The synthesizer does BFS over action sequences up to maxSynthesisLen, and for each candidate runs SciPy shgo global optimization against the cheap polynomial to find profitable parameters.
  • Counter-example loop. Candidate parameters are validated by concrete forge execution. When actual profit diverges from the polynomial estimate by >5%, that point is logged as a counter-example, re-executed on-fork, added to the data, and the polynomial is refit — correcting the surrogate exactly where it mispredicts.
  • Pruning. Low-profit sequences are dropped, the worklist is capped, and late rounds discard traces far below the global best.

The whole loop: cheap polynomial to search a huge space fast; concrete EVM execution to validate and to fix the polynomial where it is wrong.

6. What the modernization must automate

Everything in Section 3 is the expert-heavy surface PROPOSAL.md item #1 targets: identifying the protocol's actions, their token flows and parameter ranges, writing the actionStr / collectorStr snippets and transit logic, and the attack.t.sol setup. The engine (Sections 4–5) stays fixed.

Environment & reproducibility

Checked on this machine (macOS arm64) — the tool does not yet run out of the box:

  • RPC endpoint is live. The committed Alchemy mainnet endpoint still responds. (It is shared and may be closed later; plan to supply your own in settings.toml / run.sh.)
  • Foundry: not installed. The README pins a 2023 build: foundryup -C 5be158b. The revert-string and dependencyCheck parsing depend on forge's exact log/color output format, so a modern forge may break the Python scrapers. The version pin is a real reproducibility risk to resolve during the baseline run.
  • Python: 3.9 present, 3.7 (per README) absent. Deps in requirements.txt (numpy 1.21.6, scipy 1.7.3, web3, sympy, scikit-learn, …) are not installed.

Next step (deferred at user request): install Foundry + Python deps and reproduce the Euler run end-to-end to confirm the loop executes and to pin down exactly what breaks.
